## 2. 为什么要拆出 Agent 运行时

### 2.1 问题

原有能力是 **Cursor / Claude 环境里的 Skills**。Skills 能跑起来，靠的是宿主环境天然提供的 harness：

1. **工具调用循环**：模型发起 `python3 scripts/fetch.py <url>`，宿主执行并把结果喂回模型，循环直到收敛。
2. **会话状态**：多轮之间保留上下文，支持「先拆后写」这种强顺序依赖。
3. **文件读写**：`references/*.md` 按需读取，产物落到 `output/`。
4. **上下文压缩**：长会话自动摘要。

Java 后端本身**不具备**这四项能力。如果在 Java 里硬写，等于自己实现一个 harness——工具注册、JSON Schema 校验、多 provider 的 tool-calling 差异归一化、流式事件解析、重试与压缩，工作量大且与业务无关。

### 2.2 决策

把 harness 作为**独立进程 + 可替换 SPI**：

- Java 只做业务编排（参数抽取、提示词拼装、质量门、额度、持久化），这部分是纯逻辑，好测。
- harness 只做「给定 system prompt + messages + tools，跑到收敛，返回文本与用量」。
- 两者之间是一份**与 harness 无关**的 HTTP 契约。

这样换 harness 只需换一个实现，业务代码零改动。用户提到后续可能切到 deepseek harness 或其它架构，正是这个设计要覆盖的场景。

### 2.3 为什么首版选 pi

| 需求 | pi 的对应能力 |
| --- | --- |
| 多 provider 可替换 | `@earendil-works/pi-ai` 归一化 OpenAI / Anthropic / Google / **DeepSeek** / Ollama 等的 tool-calling 与流式事件 |
| Agent 循环 | `@earendil-works/pi-agent-core` 的 `Agent` 类，支持自定义工具、`beforeToolCall` / `afterToolCall` 钩子 |
| 成本可观测 | 最终消息自带 `usage.input / output / cost.total` |
| 单测无需真实 key | 自带 `fauxProvider()` 脚本化响应 |
| 许可 | MIT |

pi 是 TypeScript 实现，**无法**在 JVM 内嵌，所以只能是独立进程。这不是妥协——独立进程反而让 harness 能单独重启、单独扩容、单独换掉。

## 4. Harness 抽象（核心设计）

### 4.1 SPI

```java
public interface HarnessClient {
    /** harness 名称，如 pi / deepseek / mock */
    String name();

    /** 跑一次到收敛 */
    HarnessRunResult run(HarnessRunRequest request);

    /** 健康检查 */
    HarnessHealth health();
}
```

请求与结果是**纯数据**，不出现任何 pi 专有概念：

```java
record HarnessRunRequest(
    String requestId,      // 幂等键
    String scene,          // SCRIPT_GENERATE / SCRIPT_REWRITE / ...
    ModelSpec model,       // provider + modelId + 采样参数
    String systemPrompt,
    List<Msg> messages,    // role + content
    List<String> tools,    // 允许的工具名，空表示纯文本生成
    Integer maxSteps,
    Integer timeoutMs
) {}

record HarnessRunResult(
    String requestId,
    boolean ok,
    String text,           // 最终文本
    Usage usage,           // inputTokens / outputTokens / costUsd
    int steps,
    String harnessName,
    String harnessVersion,
    String errorCode,
    String errorMessage
) {}
```

### 4.2 实现矩阵

| 实现 | 装配条件 | 说明 |
| --- | --- | --- |
| `PiHarnessClient` | `harness.provider=pi`（默认） | HTTP 调 agent sidecar |
| `MockHarnessClient` | `harness.provider=mock` | 按场景返回结构合法的假数据，单测与无网开发用 |
| `DeepseekHarnessClient` | `harness.provider=deepseek` | 预留。只要新 harness 能满足同一份 HTTP 契约，加一个类即可 |

切换只改一行配置：

```yaml
harness:
  provider: pi          # pi | mock | deepseek
  pi:
    endpoint: http://127.0.0.1:8790
    timeout-ms: 180000
```

### 4.3 契约（Java ↔ Agent）

```
POST /v1/harness/run
{
  "requestId": "…", "scene": "SCRIPT_GENERATE",
  "model": { "provider": "deepseek", "modelId": "deepseek-chat",
             "temperature": 0.8, "maxTokens": 4096, "thinking": "off" },
  "systemPrompt": "…", "messages": [ { "role": "user", "content": "…" } ],
  "tools": [], "maxSteps": 1, "timeoutMs": 180000
}
→ 200
{
  "requestId": "…", "ok": true, "text": "…",
  "usage": { "inputTokens": 1820, "outputTokens": 960, "costUsd": 0.0031 },
  "steps": 1, "harnessName": "pi", "harnessVersion": "0.85.0"
}

GET /v1/harness/health
→ { "ok": true, "harnessName": "pi", "harnessVersion": "0.85.0",
    "providers": [ { "name": "deepseek", "ready": true }, … ] }
```

契约里没有任何 pi 特有字段。`tools` 是**工具名白名单**而非工具定义——工具实现属于 harness 侧，Java 只声明本场景允许用哪些。这样换 harness 时 Java 侧不需要搬运工具的 JSON Schema。

## 5. 模型可配置（按场景独立）

### 5.1 场景枚举

| 场景 | 用途 | 典型选型考虑 |
| --- | --- | --- |
| `TOPIC_TITLE` | 选题 + 标题 | 快、便宜，可用小模型 |
| `SCRIPT_GENERATE` | 写口播正文 | 长文质量优先 |
| `SCRIPT_DEAI` | 去 AI 味重写 | 风格改写能力优先，可与生成不同厂商 |
| `SCRIPT_REWRITE` | 洗稿十一段 | 长上下文 + 强结构遵循 |
| `VIDEO_EXTRACT` | 拆解 | 需要工具调用能力 |

**脚本生成与文案重写是两条独立配置**，这是需求明确要求的。实际上去 AI 味也独立成一个场景，因为把「写」和「改」交给不同模型，去味效果通常更好。

### 5.2 解析优先级

```
请求级覆盖（管理端调试用）
      ↓ 没有则
数据库 sv_ai_model_config（scene 唯一，enabled=1）
      ↓ 没有则
application.yml 的 ai.scenes.<scene> 默认值
      ↓ 没有则
ai.default 全局兜底
```

`ModelConfigService` 带本地缓存（默认 60 秒）+ 配置更新即失效，做到热更新且不给数据库压力。

### 5.3 密钥处理

数据库只存**环境变量名**（如 `DEEPSEEK_API_KEY`），不存密钥本身。Agent 侧由 pi-ai 按 provider 自动从环境变量解析。Java 全程不接触密钥。

## 6. 关键流程的架构取舍

### 6.1 异步任务

LLM 调用慢且不稳定，所以生成、洗稿、拆解一律异步：

```
提交 → 建 sv_task（PENDING）+ 预扣额度 → 返回 taskId
     → 线程池取任务 → 逐条执行 → 逐条入库并更新 doneCount
     → 终态 SUCCESS / PARTIAL / FAILED → 失败条目退额度
前端 → 轮询 GET /api/tasks/{id}（2s）→ 渐进渲染
```

首版用 Spring 的 `ThreadPoolTaskExecutor` + 数据库状态，不引入 MQ。理由：单机足够，且任务状态本来就要落库给前端轮询，MQ 会多一份状态源。后续要水平扩容时，把 `TaskRunner` 的取任务逻辑换成基于数据库的乐观锁抢占即可，接口不变。

### 6.2 质量门放在 Java 而非模型

`check.py` 的规则（章数、字数、禁用词、连续重合 ≥16 字、低分项）是**确定性**的，交给模型自检不可靠。所以在 Java 侧用 `QualityGate` 复刻：

- 中文字数用 `codePointCount` 去空白后统计，避免 emoji 与代理对算错。
- 连续重合检测用滑动窗口 + 后缀哈希，对 16 字窗口做 O(n) 比对。
- 命中则触发一次定向重写（把失败原因作为新的 user message 追加），最多重试 1 次，仍失败则该条标 `FAILED` 并退额度。

### 6.3 前端与原型的一致性

H5 必须 1:1 还原原型的布局、色调与交互。做法是**直接复用原型的组件与样式**，只替换数据来源：

| 原型 | H5 |
| --- | --- |
| `localStorage` 读写 | `/api` 调用 + React Query 式缓存 |
| `lib/generate.ts` 本地假生成 | `POST /api/scripts/generate` + 轮询 |
| `data/config.ts` 硬编码选项 | `GET /api/options` 下发，同文件保留为兜底默认值 |
| `data/scripts.ts` 内置样稿 | 首次登录由服务端播种，或空库 |

设计令牌（`--primary: #3f3ca8` 等）与 `@theme inline` 映射原样保留，不重新调色。

## 7. 安全设计

| 项 | 做法 |
| --- | --- |
| 认证 | JWT（HS256，2 小时）+ 服务端会话校验；`Authorization: Bearer` |
| 授权 | 所有业务查询强制带 `user_id`；越权访问返回 403 而非 404，避免探测 |
| 验证码 | 6 位数字，5 分钟有效，60 秒重发间隔，同手机号每日上限 10 条 |
| 密钥 | 仅环境变量；数据库存变量名；日志脱敏 |
| Agent 端口 | 只监听 `127.0.0.1`，不对外暴露；Java 与之同机或走内网 |
| 工具执行 | Agent 侧工具白名单，按场景下发；不提供任意 shell |
| 上传 | 录屏文件限类型与大小，存私有目录，鉴权回源 |
| 越权删除 | 删除文案先校验归属，软删除 |

## 8. 关键架构决策记录（ADR）

| 编号 | 决策 | 备选 | 理由 |
| --- | --- | --- | --- |
| ADR-1 | harness 独立进程 + SPI | 在 Java 内自研 harness | pi 是 TS 实现无法内嵌；独立进程让 harness 可单独替换与重启，正对「后续换 deepseek harness」的诉求 |
| ADR-2 | 契约里只传工具名白名单 | 传完整工具 JSON Schema | 工具实现属 harness 侧，Java 不搬运 Schema，换 harness 时业务零改动 |
| ADR-3 | 模型配置按场景分行 | 全局一套模型 | 需求明确要求脚本生成与文案重写独立；且去味用另一家模型效果更好 |
| ADR-4 | 质量门用 Java 确定性实现 | 交给模型自检 | `check.py` 规则是确定性的，模型自检会给自己放水（Skill 里专门写了「改文案不改分数」） |
| ADR-5 | 异步任务用线程池 + 数据库状态 | 引入 RabbitMQ / Redis Stream | 任务状态本就要落库供轮询，MQ 会多一份状态源；单机够用，扩容时换抢占逻辑即可 |
| ADR-6 | 复用 Skills 的 Python 脚本 | 用 Java 重写取件与 ASR | 脚本里固化了抖音 Cookie、短链还原、Whisper 重切分等踩坑经验，重写等于重新踩 |
| ADR-7 | H5 直接复用原型组件 | 按设计稿重写 | 要求 1:1 还原，复用组件是唯一能保证像素级一致的方式 |
| ADR-8 | 选项由服务端下发 | 前端硬编码 | 25 宫格与爆款元素属运营配置，改动不该发版 |
| ADR-9 | 额度预扣 + 失败退回 | 成功后再扣 | 防止并发下超额生成；预扣使额度成为准入门槛 |
| ADR-10 | MyBatis-Plus 而非 JPA | Spring Data JPA | 本项目多为明确的单表读写与分页，MyBatis-Plus 的条件构造器更直观，也便于写复杂统计 |

## 9. 部署形态

### 9.1 本地开发

仓库根目录 `./start.sh`：自动安装依赖、导入库表（已存在则跳过）、后台拉起三个进程。可重复执行。

```
./start.sh            # H5 :5173  ·  server :8080  ·  agent :8790  ·  mysql :3306
./start.sh stop
./start.sh status
```

手动等价于：

```
h5     :5173   npm run dev（代理 /api → 8080）
server :8080   mvn spring-boot:run
agent  :8790   npm run dev
mysql  :3306
```

### 9.2 生产

```
        Nginx :443
        ├── /            → h5 静态资源
        └── /api         → server:8080
                             └── 内网 → agent:8790（仅 127.0.0.1）
```

Agent 与 Server 同机部署，Agent 不暴露公网。若要独立扩容，把 Agent 放内网并在 Java 侧配置多 endpoint 轮询即可（`HarnessClient` 实现内部负载，接口不变）。

### 9.3 环境变量

| 变量 | 用途 |
| --- | --- |
| `DB_URL` / `DB_USER` / `DB_PASSWORD` | 数据库 |
| `JWT_SECRET` | 令牌签名 |
| `HARNESS_ENDPOINT` | Agent 地址 |
| `DEEPSEEK_API_KEY` / `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `GEMINI_API_KEY` | 各 provider 密钥，按需设置 |
| `SKILLS_DIR` | Agent 定位 Python 脚本的根目录 |
